Frontend och backend

En server är ett program som lyssnar

server.js 
const app = express();

// När någon frågar efter fikorna …
app.get("/api/fikor", (req, res) => {
  // … hämta dem ur databasen och svara
  res.json(hamtaFikor());
});

// Lyssna på port 3000
app.listen(3000);
  • Ett program som startar och sedan väntar på frågor, dygnet runt
  • Skrivs ofta i JavaScript med Node.js och Express, men kan skrivas i nästan vilket språk som helst
  • En port är som en dörr med ett nummer. Samma dator kan ha många servrar på olika portar
  • Nu förstår vi varför vi installerade Node.js första gången: det kör JavaScript utanför webbläsaren, till exempel en server.
  • Express är ett paket från npm som gör det enkelt att skriva en server. Agenten väljer det ofta.

HTTP

Språket klient och server pratar

HTTP

En fråga, ett svar

Fråga · request
GET /api/fikor HTTP/1.1
Host: localhost:3000
Accept: application/json
Svar · response
HTTP/1.1 200 OK
Content-Type: application/json

[{ "id": 1, "namn": "Kanelbulle" },
 { "id": 2, "namn": "Kaffe" }]
  • Allt på webben är frågor och svar som ser ut så här, i vanlig text
  • Klienten frågar alltid först. Servern svarar på exakt en fråga i taget
  • HTTP står för HyperText Transfer Protocol. Ett protokoll är en överenskommelse om hur man pratar.
  • Det här är vad Network-fliken i Dev Tools visar. Varje rad där är en sådan fråga och ett sådant svar.
  • HTTPS är samma sak, men inslaget i ett krypterat kuvert så att ingen på vägen kan läsa det.
HTTP

Fyra delar i en fråga

Fråga · request
POST /api/fikor HTTP/1.1
Content-Type: application/json
Authorization: Bearer hemlig-nyckel

{ "namn": "Semla" }
  • 🏷️Metod: vad du vill göra, här POST för att skapa något
  • 📍Adress: vad det gäller, här /api/fikor
  • 📎Headers: extra information, till exempel format och nyckel
  • 📦Body: själva innehållet. En GET har ingen
  • Svaret har samma form: en statuskod i stället för metod och adress, sedan headers och body.
  • Authorization-headern är där API-nycklar och inloggningar oftast skickas.
HTTP

Metoderna: vad vill du göra?

GET

Hämta

Visa alla fikor. Ändrar ingenting.

POST

Skapa

Lägg till en ny fika i listan.

PUT

Ändra

Byt namn på en fika. PATCH ändrar en del.

DELETE

Ta bort

Stryk en fika från listan.

När du skriver en adress i webbläsaren gör den alltid en GET.

  • Det här är skapa, läsa, ändra och ta bort. På engelska CRUD: Create, Read, Update, Delete. Nästan alla appar är CRUD i grunden.
HTTP

Statuskoder: hur gick det?

✅

200 OK

Det gick bra, här är svaret.

🆕

201 Created

Det gick bra, något nytt har skapats.

🙅

400 Bad Request

Det du skickade var fel, till exempel ett tomt namn.

🔒

401 / 403

Vem är du? / Du får inte göra det här.

🔍

404 Not Found

Det finns inget på den adressen.

💥

500 Server Error

Något gick sönder i backenden.

Tumregel: 2 = gick bra, 3 = titta någon annanstans, 4 = klientens fel, 5 = serverns fel.

  • Vi såg 200, 304, 404 och 500 i Network-fliken förra gången. Nu kommer 201, 400, 401 och 403 till.
  • 401 såg vi också när OpenWeatherMap-nyckeln inte var aktiv än.
  • Vid 500: titta i terminalen där backenden körs. Där står felet, inte i webbläsaren.
HTTP

JSON: data som text

JSON 
[
  {
    "id": 1,
    "namn": "Kanelbulle",
    "antal": 12,
    "glutenfri": false
  },
  {
    "id": 2,
    "namn": "Kaffe",
    "antal": 8,
    "glutenfri": true
  }
]
  • Det vanligaste formatet för data mellan frontend och backend
  • [ ] är en lista, { } är en sak med egenskaper: namn och värde
  • Text står inom citattecken, siffror och true/false utan
  • Lätt för både människor och program att läsa
  • JSON står för JavaScript Object Notation. Vi såg det i Application-fliken förra gången: localStorage sparade fikalistan som JSON.

REST

Ett sätt att ordna adresserna

REST

Varje sak har en adress

🌐 localhost:3000
📁 /api/fikor alla fikor
📄 /api/fikor/1 kanelbullen
📄 /api/fikor/2 kaffet
📁 /api/personer
📄 /api/personer/7
  • REST är ett mönster för hur ett API ordnar sina adresser
  • Sakerna kallas resurser: fikor, personer, recept
  • Adressen säger vad, metoden säger vad du vill göra med det
  • REST är inget program, bara en överenskommelse om hur adresserna ska se ut. De flesta API:er man stöter på följer det, till exempel GitHubs och OpenWeatherMaps.
  • API betydde ”ett sätt för program att prata med varandra”. Ett REST-API är ett sådant, över HTTP.
REST

Metod + adress = handling

MetodAdressBetyderSvar
GET/api/fikorHämta alla fikor200 + lista
GET/api/fikor/2Hämta fika nummer 2200 eller 404
POST/api/fikorSkapa en ny fika201 + den nya
PUT/api/fikor/2Ändra fika nummer 2200
DELETE/api/fikor/2Ta bort fika nummer 2204, tomt svar
  • Det här är hela API:et för en enkel app. Fem rader. Agenten skriver dem, men du kan läsa den här tabellen och förstå vad appen kan.
  • Be agenten: ”Visa mig en tabell över alla adresser i API:et.” Det är ett utmärkt sätt att granska en backend.
REST

Frontenden frågar med fetch

app.js · i webbläsaren 
// Lägg till en fika
const svar = await fetch("/api/fikor", {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({ namn: "Semla" }),
});

if (svar.status === 201) {
  visaFikor();
}
  • fetch är webbläsarens sätt att skicka en HTTP-fråga från JavaScript
  • Känner du igen delarna? Metod, adress, headers och body
  • Den syns som typ fetch i Network-fliken. Klicka på raden för att se frågan och svaret
  • Samma sak som väderappen gjorde mot OpenWeatherMap. Skillnaden är att servern nu är din egen.
Prova själv

Prata HTTP från terminalen

$ curl https://jsonplaceholder.typicode.com/users/1
{ "id": 1, "name": "Leanne Graham", "username": "Bret", … }

$ curl -i https://jsonplaceholder.typicode.com/users/999
HTTP/2 404
# -i visar svarets första rad och headers också

$ curl -X POST localhost:3000/api/fikor -H "Content-Type: application/json" -d '{"namn":"Semla"}'
# så testar du din egen backend utan någon frontend

curl finns på både Windows och Mac. Det är också så agenten testar backenden.

  • Visa live. JSONPlaceholder är ett gratis övnings-API som vi använder i övning 7. Det låtsas spara det du skickar.
  • I PowerShell på Windows: skriv curl.exe i stället för curl, annars används ett annat inbyggt kommando. Det står i övning 7.

Var bor datan?

Från arbetsminne till databas

Datalagring

Fyra ställen att spara data på

💭

Minnet

Enklast, men allt försvinner när servern startas om.

📄

En fil

Till exempel fika.json. Okej för lite data och en användare i taget.

🗄️

En databas

SQLite är en hel databas i en enda fil. Perfekt för att börja.

☁️

En databastjänst

PostgreSQL hos till exempel Supabase. För appar på riktigt.

Idag: SQLite. Samma tänk gäller för de stora databaserna.

  • localStorage från förra gången var också ett sätt att spara, men i webbläsaren. Nu sparar vi på servern, så att alla klienter ser samma data.
  • Node har SQLite inbyggt (node:sqlite), så inga extra installationer behövs.
Datalagring

En databas är tabeller

Tabellen fikor
idnamnantaltillagd_av

2Kaffe8Ali

  • Som ett kalkylark: en tabell per sorts sak, en rad per sak
  • Kolumnerna bestäms i förväg: namn är text, antal är ett tal
  • Varje rad får ett unikt id. Det är siffran i /api/fikor/4
  • Hur tabellerna ser ut kallas databasens schema. Agenten föreslår det i sin plan. Läs det: saknas en kolumn du behöver?
Datalagring

SQL: språket databasen förstår

SQL 
-- Hämta alla fikor, flest först
SELECT * FROM fikor
ORDER BY antal DESC;

-- Lägg till en ny
INSERT INTO fikor (namn, antal)
VALUES ('Semla', 10);

-- Ta bort nummer 2
DELETE FROM fikor WHERE id = 2;
  • Backenden översätter HTTP-frågor till SQL
  • GET blir SELECT, POST blir INSERT, DELETE blir DELETE
  • Agenten skriver all SQL. Det räcker att du känner igen den
  • SQL uttalas ”es-ku-ell” eller ”sequel”. Språket är 50 år gammalt och finns överallt.
  • Med ett verktyg som DB Browser for SQLite kan man öppna databasfilen och titta i tabellerna, som i ett kalkylark.

Backend på riktigt

Säkerhet, felsökning och publicering

Säkerhet

Lita aldrig på klienten

  • 🕵️Vem som helst kan skicka vad som helst till din backend, med curl, utan att gå via din fina frontend
  • 🛂Backenden kontrollerar allt: tomma fält, för långa texter, fel typ av data
  • 🔑Hemligheter bor på servern i en .env-fil som aldrig hamnar i Git. Nu kan nyckeln äntligen hållas hemlig
  • 🚪Publicerar du? Då behövs inloggning, annars kan alla ändra i din data
  • Koppla till API-nycklarna förra gången: i en webbapp syns nyckeln. Med en backend kan frontenden fråga din server, som i sin tur frågar OpenWeatherMap med nyckeln. Nyckeln lämnar aldrig servern.
  • Skriv in i prompten: ”Kontrollera all data som kommer in till API:et och svara med 400 och ett tydligt felmeddelande om något är fel.”
Felsökning

Vanliga fel och vad de betyder

🔌

Failed to fetch

Frontenden når inte backenden. Är servern igång? Rätt port?

🚧

CORS error

Webbläsaren stoppar frågan för att frontend och backend har olika adresser. Ge felet till agenten.

🚪

EADDRINUSE

Porten är upptagen. En gammal server kör redan. Stäng den eller byt port.

💥

500 i Network

Felet syns inte i webbläsaren. Titta i terminalen där backenden körs.

  • CORS är det klassiska backendfelet. Det är en säkerhetsfunktion i webbläsaren, och lösningen är en inställning i backenden. Agenten vet hur.
  • Med en backend finns det två ställen att leta efter fel: Console i webbläsaren och backendens terminal. Ge agenten båda.
Publicering

GitHub Pages räcker inte längre

  • GitHub Pages skickar bara färdiga filer. Den kan inte köra ett program
  • En backend behöver en dator som alltid är på: en molntjänst som Render, Railway eller Fly.io
  • Databasen behöver ofta en egen tjänst, till exempel Supabase
  • Gratisnivåerna somnar ofta när ingen använder dem och har gränser. Läs villkoren
🏠

Idag: localhost

Vi kör backenden på vår egen dator. Det räcker för att förstå hur allt hänger ihop.

  • Fråga agenten: ”Hur kan jag publicera den här appen med backend gratis, och vad är begränsningarna?” Den vet vilka tjänster som passar.
  • En SQLite-fil på en gratis molntjänst kan försvinna vid omstart. Därför används ofta en separat databastjänst när man publicerar.
Bonus · Fly.io

Fly.io: en server som kostar en fika i månaden

  • Fly.io kör din backend på riktiga servrar i datorhallar runt om i världen
  • Inte gratis: du betalar per sekund som servern är igång. Minsta servern kostar 2,19 dollar i månaden, drygt 20 kronor, om den aldrig sover
  • En disk för SQLite-filen: 0,15 dollar per GB i månaden
  • Provperiod utan kort: 2 timmar serverdrift eller 7 dagar. Sedan krävs kreditkort
💤

Servern får sova

Fly.io stänger av servern när ingen använder appen och väcker den vid nästa besök. Då blir det ännu billigare.

  • Priserna gällde i november 2026. Fly.io höjde priset på minne i oktober 2026, så be deltagarna kolla prissidan själva.
  • Viktigast: fly apps destroy tar bort appen och stoppar kostnaden.
