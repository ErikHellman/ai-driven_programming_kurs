Anna är inloggad

Supabase är din backend i flödet. Din app pratar bara med Supabase, aldrig direkt med GitHub.

  • Jämför med flödet i del 1. Det är samma, men Supabase har tagit backendens roll: det är Supabase som har client secret och byter koden mot Annas uppgifter.
  • Användarna hamnar i en färdig tabell, auth.users. Den syns under Authentication på supabase.com.
Supabase Auth

Det här gör du själv

🐙GitHubSettings → Developer settings → OAuth Apps → New OAuth App. Klistra in Supabases callback-adress.
🔐HemlighetenSkapa en client secret och spara den i lösenordshanteraren direkt. Den visas bara en gång.
⚡SupabaseAuthentication → Sign In / Providers → GitHub. Klistra in client ID och client secret.
↩️AdressernaAuthentication → URL Configuration: localhost och din adress på GitHub Pages.

Agenten skriver koden. Konton och hemligheter sköter du, precis som med API-nycklarna i tillfälle 2.

  • Callback-adressen ser ut som https://projektnamn.supabase.co/auth/v1/callback. Supabase visar den på samma sida där man slår på GitHub.
  • URL Configuration är det vanligaste felet: står inte appens adress där skickas man tillbaka till fel ställe efter inloggningen.
  • Hela gången står i övning 12.
Regler i databasen

Vem äger raden?

Tabellen fikor
idnamnuser_id
1Kanelbulle🟠 Anna
2Kaffe🟢 Ali
3Chokladboll🟠 Anna
  • Varje rad får en ny kolumn: vem som lade till den
  • Databasen fyller i den själv, från JWT:n. Ingen kan låtsas vara någon annan
  • Anna ser alla fikor, men kan bara ta bort rad 1 och 3
  • user_id är id:t från tabellen auth.users. I databasen heter funktionen som läser det ur JWT:n auth.uid().
  • Det här är auktorisering från del 1: inloggningen säger vem du är, reglerna säger vad du får göra.
Regler i databasen

Row Level Security

SQL · en migration 
-- Inloggade får läsa allt
create policy "läsa" on fikor
  for select to authenticated
  using (true);

-- Bara ta bort det du själv lagt till
create policy "ta bort egna" on fikor
  for delete to authenticated
  using (auth.uid() = user_id);
  • En regel per handling: läsa, lägga till, ändra, ta bort
  • auth.uid() är den inloggade, hämtad ur JWT:n
  • Ej inloggad? Då gäller inga regler, och svaret blir en tom lista
  • Agenten skriver reglerna. Du läser dem och frågar om det du inte förstår
  • Det här är den viktigaste koden i hela appen ur säkerhetssynpunkt. Fem till tio rader. Läs dem i pull requesten.
  • Be agenten: ”Förklara varje regel i en mening på svenska.” Det gör granskningen lätt.
  • Notera: RLS svarar inte 403 när man inte får läsa. Man får bara inga rader. Det förvånar många.
Regler i databasen

Att dölja knappen är inte säkerhet

🎨

I frontenden: bekvämlighet

Visa bara ta bort-knappen på dina egna fikor. Snyggt och tydligt, men vem som helst kan skicka frågan ändå.

🛂

I databasen: säkerhet

Regeln stoppar frågan, hur den än skickas. Från sidan, från curl eller från en annan sajt.

Gör båda. Men bara den ena skyddar. Samma regel som förra gången: lita aldrig på klienten.

  • Med Express i övning 8 är det servern som kontrollerar. Med Supabase direkt från frontenden, som i övning 10, är det reglerna. Någon av dem måste göra det.

Allt från del 1 i en riktig app: OAuth, JWT, auktorisering.

  • Förbered: fikalistan från övning 10 publicerad, Supabase CLI inloggad och länkad. Ha ett andra GitHub-konto eller en kollega redo för att visa en annan användare. Ha lösenordshanteraren öppen.
  • Registrera OAuth-appen hos GitHub live. Kopiera callback-adressen från Supabase. Skapa client secret och klistra in i Supabase utan att visa den länge på skärmen. Lägg till localhost och GitHub Pages-adressen under URL Configuration.
  • Prompten från övning 12, plan först. Visa migrationen: kolumnen user_id och reglerna. Be agenten förklara varje regel på svenska.
  • Logga in. Visa Network: frågorna till /rest/v1/fikor har nu Authorization: Bearer eyJ…, tre delar med punkter, som i del 1. Visa Application → Local Storage där Supabase sparar sessionen.
  • Kör curl mot /rest/v1/fikor med bara den publika nyckeln: tom lista. Logga in som någon annan och försök ta bort Annas fika: inget händer.
  • Säg ärligt: Supabase sparar inloggningen i localStorage, inte i en HttpOnly-cookie. Därför är skyddet mot XSS extra viktigt, och React hjälper oss med det.

Säkerhetsgranskning

Låt en ny session leta fel

Säkerhetsgranskning

/security-review

  • 🆕Ny session. Den som skrev koden är sämst på att hitta sina egna fel, även för en agent
  • 🔍I Claude Code: skriv /security-review på din branch. Den granskar ändringarna mot main
  • 💬I Codex eller appen: använd prompten från del 1
  • 🚫Be den inte ändra något än. Först listan, sedan bestämmer du
🧠

Nu förstår du svaret

JWT, RLS, XSS, CORS och rate limiting. Orden från del 1 är orden granskningen använder.

  • Visa live på demoappen direkt efter demon. Det tar ett par minuter.
  • Granskningen hittar ofta saker även i en liten app: ingen gräns för hur långt namnet får vara, inga begränsningar av antal frågor, saknad Content-Security-Policy.

Agenten kan ha fel åt båda hållen. Den missar saker, och den larmar i onödan.

  • Bra följdfråga till agenten: ”Beskriv steg för steg hur någon skulle utnyttja det här.” Kan den inte det är det ofta ett falsklarm.
  • För appar med andras personuppgifter eller pengar räcker inte agenten. Då behövs en människa som kan säkerhet.

Agenten och säkerheten

Vad får agenten göra?

✅

Tillåt gärna

Läsa koden, köra npm test, starta servern, skapa en branch.

🤔

Läs först

Installera paket, ändra databasen, git push, publicera.

🛑

Nej, eller bara du

Radera mappar, skriva om historiken med --force, ta bort ett Supabase-projekt.

Klicka inte bara ”ja” på allt. Frågan är agentens sätt att låta dig bestämma.

  • Claude Code frågar innan den kör kommandon och ändrar filer. Man kan tillåta vissa kommandon permanent i inställningarna. Codex har liknande lägen: bara läsa, fråga först, eller full åtkomst.
  • Läget där agenten gör allt utan att fråga är bekvämt, men använd det bara i ett projekt som ligger i Git och där inget hemligt finns på datorn som agenten kan nå.
  • Git är skyddsnätet från tillfälle 1: en commit innan agenten börjar gör att allt kan ångras.
Agenten och säkerheten

Hemligheter och agenten

  • 💬Aldrig i chatten. Allt du skriver skickas till leverantören och sparas i historiken
  • 📄Agenten kan läsa .env om du inte säger nej. I Claude Code kan du förbjuda det i .claude/settings.json
  • 🙈.env i .gitignore, och GitHub stoppar många nycklar som någon försöker pusha
  • 🔄Läckt ändå? Byt nyckeln direkt. Att ta bort committen hjälper inte, den kan redan vara kopierad
  • I tillfälle 2 sa vi: nyckeln i lösenordshanteraren, aldrig i chatten. Nu vet vi varför: chatten är en text som skickas och sparas hos någon annan.
  • Exempel på .claude/settings.json: { "permissions": { "deny": ["Read(./.env)", "Read(./.env.*)"] } }. Be agenten lägga in det åt dig.
  • GitHub kallar funktionen push protection. Den känner igen nycklar från många tjänster och stoppar pushen.
  • Att byta nyckel heter rotera. Alla tjänster har en knapp för det: Supabase, Resend, OpenWeatherMap, GitHub.

Nästa gång bygger vi en app som själv använder en LLM. Då blir det här din apps problem.

  • Kommentaren i exemplet syns inte när sidan visas, men agenten läser källkoden. Det är det som gör det lömskt.
  • Modellerna blir bättre på att stå emot, men det finns inget fullständigt skydd. Därför är behörigheterna på förra sliden så viktiga: en agent som inte får skicka saker till nätet kan inte läcka dem.
  • Brygga till tillfälle 5: när användare skriver till en LLM i din app kan de försöka samma sak.
