🔀 Din första pull request

Lägg till en ny funktion i en app du redan har byggt. Den här gången med en riktig prompt, en minneslapp för agenten, tester som GitHub kör åt dig, regler som skyddar main och en pull request som du granskar innan något ändras.

Syftet med övningen: att öva på arbetsflödet från del 1. Tester med GitHub Actions, ett ruleset för main, prompt med fem delar, plan först, branch, pull request, granskning och merge. Själva funktionen är inte det viktiga.

Innan du börjar: du behöver en app som redan ligger på GitHub, till exempel från övning 1 eller övning 3. Har du ingen? Be agenten bygga en liten app och lägga upp den på GitHub med gh först, som i övning 1.

  1. Öppna projektet och kolla läget

    Öppna appens mapp i Claude-appen (fliken Code) eller ChatGPT-appen (Codex). Börja med en ny session och fråga:

    Prompt 
    Vilken branch är jag på, finns det ändringar som inte är sparade, och är allt pushat till GitHub? Ändra ingenting.

    Står det att du har osparade ändringar? Be agenten spara dem med en commit och pusha, så att du börjar från ett rent läge på main.

    Rulesets är gratis för publika repon. Är ditt repo privat kan agenten göra det publikt med gh repo edit, om det inte finns något hemligt i det.

  2. Skapa minneslappen AGENTS.md

    Be agenten skriva filen. Den läser igenom projektet och skriver ner det viktigaste om appen. Filen läses av både Claude Code och Codex.

    Prompt 
    Läs igenom projektet och skriv en kort AGENTS.md med det viktigaste om appen: vad den gör, vilken teknik den använder och hur man startar och testar den. Visa mig filen när du är klar.

    Öppna filen i VS Code och läs den. Stämmer det? Lägg till två regler längst ner, med egna ord:

    Lägg till i AGENTS.md 
    ## Arbetssätt
- Jobba alltid på en ny branch, aldrig direkt på main.
- Kör testerna innan du öppnar en pull request. De ska gå igenom.
- När du är klar: pusha branchen och öppna en pull request med gh.

    Nu behöver du inte skriva det i varje prompt. Filen följer med till alla framtida sessioner.

  3. Tester som GitHub kör åt dig

    Be agenten skriva några tester och en fil för GitHub Actions som kör dem på varje pull request:

    Prompt 
    Lägg till några enkla tester för appen, så att vi märker om något går sönder. Lägg också till ett GitHub Actions-workflow i .github/workflows/test.yml som kör testerna på varje pull request. Jobbet ska heta test. Lägg till AGENTS.md från förra steget i samma ändring. Jobba på en ny branch, öppna en pull request med gh och ge mig länken.

    Öppna länken och scrolla ner till kontrollerna. Först en gul prick medan testerna körs, sedan en grön bock. Klicka på Details för att se vad GitHub gjorde. Slå sedan ihop pull requesten med Merge pull request.

    Rött kryss?

    Be agenten: Kolla varför kontrollerna på pull requesten misslyckas och rätta det. Pusha till samma branch. Ladda om sidan när den är klar.

  4. Skydda main med ett ruleset

    Ett ruleset är regler för en branch. Nu bestämmer vi att main bara får ändras via en pull request med gröna tester. Agenten ställer in det med gh:

    Prompt 
    Skapa ett ruleset för main i det här repot med gh api. Det ska heta Skydda main och kräva en pull request före merge (men inga godkännanden, jag jobbar ensam), kräva att kontrollen test har gått igenom, och förbjuda force push och att main tas bort. Visa kommandot och förklara det innan du kör det.

    Kolla resultatet på två sätt:

    Terminal 
    gh ruleset list

    Öppna också repot på GitHub och gå till Settings → Rules → Rulesets. Klicka på Skydda main och läs reglerna. Stämmer de med det du bad om?

    Hur ser kommandot ut?

    Agenten skickar reglerna som JSON till GitHubs API. Ungefär så här, men du behöver inte skriva det själv:

    Exempel 
    gh api repos/{owner}/{repo}/rulesets --method POST --input ruleset.json
    ruleset.json 
    {
  "name": "Skydda main",
  "target": "branch",
  "enforcement": "active",
  "conditions": { "ref_name": { "include": ["~DEFAULT_BRANCH"], "exclude": [] } },
  "rules": [
    { "type": "deletion" },
    { "type": "non_fast_forward" },
    { "type": "pull_request", "parameters": {
        "required_approving_review_count": 0,
        "dismiss_stale_reviews_on_push": false,
        "require_code_owner_review": false,
        "require_last_push_approval": false,
        "required_review_thread_resolution": false } },
    { "type": "required_status_checks", "parameters": {
        "strict_required_status_checks_policy": false,
        "required_status_checks": [ { "context": "test" } ] } }
  ]
}

    non_fast_forward betyder att ingen får skriva över historiken med force push. ~DEFAULT_BRANCH betyder repots huvudbranch, alltså main.

    Vill du se att det fungerar? Be agenten Försök pusha en tom commit direkt till main och berätta vad som händer. Ångra sedan committen lokalt. GitHub säger nej. 🛡️

  5. Välj en funktion och skriv prompten

    Välj något litet som går att göra på en kvart. Några idéer:

    • Ett mörkt läge med en knapp för att byta.
    • En sökruta som filtrerar listan.
    • En knapp som exporterar allt till en fil, och en som importerar.
    • En räknare som visar hur många saker som finns i listan.

    Skriv prompten med de fem delarna från del 1. Börja gärna i en fil i VS Code, så kan du ändra i lugn och ro.

    DelFråga dig självExempel
    🎯 MålVad ska byggas, och varför?Lägg till en sökruta i receptboken så att jag snabbt hittar ett recept.
    🗺️ SammanhangVar i appen? Vad finns redan?Sökrutan ska ligga ovanför receptlistan.
    📏 Krav och gränserHur ska det bete sig och se ut? Vad ska inte röras?Sök på både namn och ingredienser. Stora och små bokstäver spelar ingen roll. Ändra inte hur recepten sparas.
    ✅ Klart närHur vet ni att det fungerar?Klart när jag kan skriva ”lök” och bara se recept med lök. Testa det själv i en webbläsare innan du säger att du är klar.
    🛠️ ArbetssättHur ska agenten jobba?Visa en kort plan först och vänta på mitt okej.
    Kolla din prompt innan du skickar den
    • Skulle en ny kollega förstå vad du vill ha, utan att fråga?
    • Står det var i appen funktionen ska finnas?
    • Står det något som agenten inte ska ändra?
    • Står det hur ni vet att det fungerar?
    • Ber du om en plan först?

  6. Planläge: läs planen innan något byggs

    Välj planläget i Claude-appen innan du skickar prompten (i terminalen växlar du dit med Shift + Tab). Då får agenten läsa koden men inte ändra något. I Codex räcker det att prompten ber om en plan först.

    Läs planen. Står det att den skapar en branch? Ändrar den filer du inte väntade dig? Rätta planen med ett svar i chatten, och säg Kör! när du är nöjd.

  7. Låt agenten öppna en pull request

    Har agenten läst din AGENTS.md öppnar den en pull request av sig själv när den är klar. Annars:

    Prompt 
    Pusha branchen och öppna en pull request med gh. Skriv en tydlig beskrivning av vad du har ändrat och hur jag testar det. Ge mig länken.

  8. Granska på GitHub

    Öppna länken. Du behöver inte förstå varje rad, du letar efter överraskningar:

    • Conversation: stämmer beskrivningen med det du bad om?
    • Files changed: vilka filer har ändrats? Grönt är nytt, rött är borttaget. Är det några filer som inte borde röras, eller mycket mer kod än du väntade dig?
    • Checks: har kontrollen test gått igenom? Är den inte grön är knappen Merge pull request låst. Det är ditt ruleset som jobbar.

    Skriv en kommentar på en rad: håll musen över raden under Files changed och klicka på det blå plustecknet. Till exempel Kan sökrutan få samma rundade hörn som knapparna? Klicka Add single comment. Be sedan agenten:

    Prompt 
    Läs kommentarerna på pull requesten och gör ändringarna. Pusha till samma branch.

    Ladda om sidan på GitHub. Ändringen syns i samma pull request.

  9. Andra ögon: låt en ny session granska

    Starta en ny session i samma projekt. Den har inte skrivit koden själv och ser den med fräscha ögon:

    Prompt 
    Granska den öppna pull requesten i det här repot med gh. Leta efter fel, saker som saknas och saker som kan förenklas. Ändra ingenting, berätta bara vad du hittar.

    Hittade den något? Be den rätta det, eller gå tillbaka till den första sessionen.

  10. Merge och publicera

    När du är nöjd: klicka på Merge pull request på GitHub, eller be agenten:

    Prompt 
    Slå ihop pull requesten med main, ta bort branchen och gå tillbaka till main lokalt.

    Publiceras appen på GitHub Pages ser du ändringen där om en minut eller två. Öppna den i mobilen. 🎉

Det gick inte som tänkt?
  • Agenten jobbade direkt på main: den läste inte regeln, eller så saknades den. Be den: Flytta mina ändringar till en ny branch och återställ main till hur den var på GitHub.
  • Ruleset kräver GitHub Pro: repot är privat. Gör det publikt, om inget hemligt finns i det, eller hoppa över det steget.
  • Merge-knappen är grå: kontrollen test är inte grön än, eller har ett annat namn än i ditt ruleset. Be agenten jämföra namnet i workflow-filen med ditt ruleset.
  • gh säger att du inte är inloggad: kör gh auth login i terminalen, se guiden för GitHub.
  • Blev det helt fel? Stäng pull requesten på GitHub med Close pull request. Main har aldrig rörts. Börja om med en ny session och en bättre prompt.

Klart?

  • Mitt projekt har en AGENTS.md som jag har läst och lagt till regler i
  • GitHub Actions kör testerna på varje pull request, och jag har sett en grön bock
  • Main skyddas av ett ruleset som agenten skapade med gh
  • Jag har skrivit en prompt med mål, sammanhang, krav och gränser, klart när och arbetssätt
  • Jag har läst planen innan agenten började bygga
  • Jag har öppnat, kommenterat och granskat en pull request på GitHub
  • Pull requesten är ihopslagen med main
