🍰 En app med egen backend

Bygg en app där alla ser samma data, med en backend, en databas och en frontend. Du delar upp arbetet i flera sessioner, och varje steg blir en egen pull request.

Syftet med övningen: att använda allt från idag på en gång. En plan i en fil, en session per steg, pull requests och en backend med REST-API och databas. Hinner du inte allt räcker det att backenden fungerar.

Innan du börjar: du behöver Node.js, Git, ett GitHub-konto med gh inloggat och Claude- eller ChatGPT-appen. Kolla med node --version i terminalen att du har version 22.13 eller senare, annars saknas den inbyggda databasen. Se guiden för Node.js.

  1. Välj ett projekt

    Alla fyra projekten är samma sorts app: en lista som många delar. Välj det som låter roligast. Startprompten nedan är för fikalistan. Väljer du ett annat projekt byter du ut första stycket och raderna under Funktioner mot dem som står under ditt projekt, och namnet på repot.

    ☕ Fikalistan för jobbet
    Startprompt · session 1 
    Jag vill bygga en gemensam fikalista för jobbet: en webbapp med en egen backend och databas, så att alla ser samma lista. Planera bara, skriv ingen kod än.

Funktioner:
- Jag kan skriva mitt namn och vad jag tar med till fikat.
- Alla ser samma lista, med det senaste först.
- Jag kan ta bort något jag har lagt till.
- Listan finns kvar när servern startas om.

Teknik:
- Backend: Node.js med Express och ett REST-API under /api.
- Databas: SQLite med Nodes inbyggda modul node:sqlite. Databasfilen ska inte in i Git.
- Backenden kontrollerar all data som kommer in och svarar med 400 och ett tydligt felmeddelande på svenska om något är fel.
- Frontend: React och Vite med JavaScript. Vite ska skicka vidare /api till backenden, så att det inte blir några CORS-fel.
- Backend och frontend i samma repo, i mapparna server och client. Ett kommando i projektets rot ska starta båda.
- Tester för API:et med Nodes inbyggda testverktyg (node --test), och ett GitHub Actions-workflow som kör testerna på varje pull request.
- Svenska i hela gränssnittet, mobilanpassat och en glad design med varma färger.

Så här jobbar vi:
- Ställ frågor till mig tills du förstår vad jag vill ha.
- Skriv sedan planen i PLAN.md. Dela upp den i steg som var och en går att göra i en egen session och blir en egen pull request. Varje steg ska ha en rad om hur vi vet att det är klart.
- Ta med en tabell över API:ets adresser (metod, adress, vad den gör och vilka statuskoder den svarar med) och hur tabellerna i databasen ska se ut.
- Skriv en kort CLAUDE.md med det som alltid gäller i projektet. Bland annat att varje steg görs på en egen branch och avslutas med en pull request som öppnas med gh, att testerna ska gå igenom innan pull requesten öppnas, och att steget bockas av i PLAN.md.
- Spara med Git, skapa ett publikt repo på GitHub med gh som heter fikalistan-backend och pusha.

  2. 📋 Session 1: planera

    Skapa en tom mapp, till exempel kurs/fikalistan-backend, och öppna den i Claude-appen (fliken Code) eller ChatGPT-appen (Codex). Klistra in startprompten.

    Agenten ställer frågor. Svara på dem. Den skriver sedan PLAN.md och CLAUDE.md, skapar repot och pushar. Öppna båda filerna i VS Code och läs dem:

    • Hur många steg blev det? Är det ungefär backend, frontend och finputs? Är ett steg för stort, be agenten dela upp det.
    • Läs tabellen över API:et. Känner du igen metoderna och statuskoderna från del 2? Saknas något användaren ska kunna göra?
    • Läs hur databasens tabeller ser ut. Finns det en kolumn för allt som ska sparas?

    Vill du ändra något, säg det i chatten och be agenten uppdatera filerna och pusha.

  3. 🗄️ Session 2: backenden

    Starta en ny session i samma mapp. Agenten minns ingenting från session 1, men den läser CLAUDE.md och kan läsa planen:

    Prompt · session 2, 3 och 4 
    Läs PLAN.md och gör nästa steg som inte är avbockat. Visa en kort plan för steget först och vänta på mitt okej. När du är klar: kör testerna, starta appen så att jag kan prova den, bocka av steget i PLAN.md, öppna en pull request med gh och ge mig länken.

    Samma prompt fungerar för alla steg. Det är planen i filen som säger vad som ska göras.

    När backenden kör: öppna http://localhost:3000/api/fikor i webbläsaren (adressen kan se lite annorlunda ut i din app, kolla tabellen i PLAN.md). Du ser JSON, precis som i övning 7. Vill du testa mer, be agenten:

    Prompt 
    Ge mig curl-kommandon som jag kan köra själv för att prova varje adress i API:et. Jag använder Windows/Mac (välj ett). Förklara vilken statuskod jag ska få.

  4. 🔀 Granska och slå ihop

    Öppna länken till pull requesten på GitHub.

    • Checks: kör GitHub Actions testerna? Vänta på grön bock. Rött kryss? Be agenten: Kolla varför kontrollerna på pull requesten misslyckas och rätta det.
    • Files changed: ser du mapparna server och testerna? Är databasfilen med? Det ska den inte vara.

    När allt är grönt: Merge pull request. Be sedan agenten Gå tillbaka till main och hämta det senaste från GitHub.

  5. 🎨 Session 3: frontenden

    Ny session, samma prompt som i session 2. Nu bygger agenten gränssnittet i React. När den är klar, öppna adressen den ger dig (oftast http://localhost:5173) och prova appen.

    Öppna Network i Dev Tools och lägg till något i listan. Hittar du din POST och statuskoden 201? Öppna sedan samma adress i en annan webbläsare. Syns samma lista? Det är backenden som gör det. 🎉

    Granska och slå ihop pull requesten precis som förut.

  6. 🔍 Session 4: andra ögon

    En ny session har inte skrivit koden själv och hittar ofta saker de tidigare missade:

    Prompt 
    Granska hela projektet med fräscha ögon. Leta efter fel, säkerhetsproblem och data som backenden inte kontrollerar. Prova också att skicka konstiga saker till API:et, till exempel ett tomt namn eller en jättelång text. Skriv vad du hittar i en lista, och fråga mig vad jag vill att du rättar.

    Välj det viktigaste och låt agenten rätta det på en branch med en pull request.

Det fungerar inte?
  • Failed to fetch eller en tom lista: backenden kör inte. Kolla terminalen, eller be agenten starta den.
  • CORS-fel i Console: frontenden frågar backenden direkt i stället för via Vite. Ge felet till agenten och påminn om att Vite ska skicka vidare /api.
  • EADDRINUSE: en gammal server kör redan på porten. Be agenten stoppa den.
  • 500 i Network: felet står i terminalen där backenden kör. Kopiera det till agenten.
  • node:sqlite finns inte: din Node.js är för gammal. Uppdatera enligt guiden och starta om terminalen.
  • Agenten minns inte vad ni bestämde: det står inte i PLAN.md eller CLAUDE.md. Be den skriva in det där.

Kan den publiceras? Inte på GitHub Pages, som bara skickar färdiga filer. Backenden behöver en molntjänst som kör den dygnet runt. Är du nyfiken, fråga agenten: Hur kan jag publicera den här appen med backend gratis, och vad är begränsningarna? Tänk på att alla som hittar adressen då kan ändra i listan, om du inte lägger till inloggning.

Klart?

  • Mitt projekt har en PLAN.md med steg och en tabell över API:et, och en CLAUDE.md
  • Varje steg gjordes i en egen session och blev en egen pull request
  • Testerna körs av GitHub Actions på varje pull request
  • Jag har sett JSON från min egen backend i webbläsaren
  • Jag har sett min egen POST och statuskoden 201 i Network-fliken
  • Samma data syns i två olika webbläsare
